### One file serving as both baseline and history will silently pick one (2026-08-08)
**Problem**: `_shape_signatures.json` was the drift gate's baseline *and* the volatility classifier's history. The two roles need opposite commit rules — baseline only on pass, history on every run — and the tripwire running before the commit step meant "baseline" quietly won.
**Root cause**: Nobody chose; the ordering chose. The classifier could only learn from runs that passed, i.e. from its own near-misses.
**Fix** (#43): split them — `_shape_observations.jsonl` is append-only, committed by its own step *before* the gate. When one artefact has two consumers with conflicting durability rules, it is two artefacts.

### `fetch-depth` was the obvious fix for a slow checkout, and it does nothing (2026-08-08)
**Problem**: The daily run's checkout takes 101s on a 797 MiB repo with `fetch-depth: 0`. Bounding the depth looks like a one-line win.
**Root cause**: `data/` is 1,029 MB of write-once timestamped files sitting *at HEAD* — 5,163 blobs against 1,187 commits, so there is no churn for history truncation to skip. Measured: depth-250 clone 784 MB vs full 792 MB, no time saved.
**Fix**: None applied — the change was withdrawn before shipping. Bound `fetch-depth` only *after* the archive leaves the working tree; alone it is a no-op. Measure a size fix before shipping it, because "smaller history" and "smaller checkout" are different problems.

### An unbounded grace is a suppressed error wearing a nicer name (2026-08-08)
**Problem**: The 2026-07-07 buurt guard coerced present-but-empty feeds to absent *unconditionally*, so a sustained Open-Meteo outage would have degraded silently forever — the same failure #38's streak counter exists to prevent for the price feeds.
**Root cause**: The guard was written to stop a transient aborting the publish, and "stop it aborting" was implemented as "stop it mattering".
**Fix** (`7ff9623`, #42): time-box it — coerce for N-1 runs, then let the gate fail loudly. If you catch a transient by ignoring it, bound how long you will ignore it.

### The memory index outgrew the project file it indexes (2026-08-08)
**Problem**: `/audit-context` found MEMORY.md at 24,053 chars — larger than CLAUDE.md (19,145) — despite its own header saying "keep lean, navigational index only". One `- **Pipeline**` bullet was 5,174 chars recapping 12 sessions.
**Root cause**: `/curate` step 3 says "update Current State to reflect what shipped" with no matching instruction to prune. Every session appended; none truncated. Eight of those sessions already had dedicated session files, themselves indexed two sections above — the same content in three layers.
**Fix**: Trimmed to 20,944 (Pipeline bullet −57%). When a curation step tells you to append to an auto-loaded file, it is also telling you to check what can leave.

### A hypothesis log earns its keep on the first check (2026-08-08)
**Problem**: H5 ("git-as-archive is viable until ~1 GB") was written with thresholds of 700 MB / 60s checkout. Both were **already exceeded** when checked hours later: 797 MiB, 101s.
**Root cause**: The belief was never measured, only assumed — the last recorded figure (3,909 files) was eight weeks old, and nothing re-checked it because the issue was tagged "defer".
**Fix**: Writing the trigger *as a number* is what surfaced it. A deferred decision needs a measurable revisit condition, not a "revisit later".

### Schema-drift fail-mode starves the volatility classifier that would have prevented it (2026-08-08)
**Problem**: Run `30838120578` (08-03) failed the drift tripwire on `ned_production` + `wind_forecast`; five days on, `derive_volatile_feeds()` still does not classify either, so the same transient will fail the same way.
**Root cause**: The tripwire (`collect-data.yml:119`) runs *before* the commit step (`:149`), so a failing run never commits its sidecar — and the classifier learns only from committed history. Drift that fails is invisible to the thing designed to learn from it; only drift that *warns* teaches.
**Fix**: None yet — filed as an issue. The self-classification decision below now records this limit.

### A guard that fires 100% of the time is worse than no guard (2026-08-08)
**Problem**: The new verification hook's workflow-YAML branch reported the valid, shipping `collect-data.yml` as "not valid YAML — the daily run would fail to start" on every single edit.
**Root cause**: PyYAML was in neither the venv nor `requirements.txt`, and `run()` could not tell `ModuleNotFoundError` from a parse error, so it printed the parse-error message and blamed the file.
**Fix**: Added PyYAML to `requirements.txt`; the hook now distinguishes the two. Lesson: an always-red guard trains you to disable it just as surely as an always-green one trains you to trust it — both destroy the signal.

### A version stamp is not an instrument; marker strings are (2026-09-06)
A project-local skill sat 20 framework releases behind while its stamp read v1.17.0 and nothing in the estate ever mentioned the file. `install-global-skills.sh --check` excludes project-local copies **by design**, so it reported a clean estate — correctly. A re-mapped copy also defeats byte comparison by construction.
**Lesson**: for a copied-and-adapted artifact, grep the marker strings the upstream release names (`/update-drift` Step 3), never the stamp. Eight markers returned 0 in a file whose stamp gave no hint.

### The three-dot diff excludes the root commit, so a "whole branch" fallback reviews nothing (2026-09-06)
`/review-changes` ported the framework's `$BASE` block, whose unresolved-baseline fallback sets `BASE=<root commit>` and diffs `"$BASE"...HEAD`. Three-dot diffs from `merge-base(BASE,HEAD)` — which *is* the root commit — so its content is excluded: a repo whose whole change is its first commit reports 0 of 1 while `git show --stat HEAD` lists the file. Measured 2 of 3 and 4 of 5 on multi-commit repos.
**Fix**: name the empty tree — `git diff --stat $(git hash-object -t tree /dev/null)..HEAD`, two dots — and treat an unresolved baseline as a finding, never a clean result. Filed upstream as agent-ready-projects#149.
**Lesson**: `$BASE` *resolving* is not `$BASE` being *right*. The guard that checks resolution passed on every one of these.

### A repair tool that over-reports reads as a finding, not as a defect (2026-09-03)
`backfill_entsoe.py` tests for `entsoe` at the TOP level, but the v2.2 envelope wrap (2026-06-07) moved the datasets under `data`. It was written 2026-03-28, when the key genuinely was top-level, and never migrated — so it reports all 108 dates degraded, including ones verified healthy (192 points each). Its patch path writes at the same wrong level, so an un-dry-run would have re-fetched ~108 dates from an ENTSO-E just out of maintenance and written `{metadata, data, entsoe, entsoe_de}` — a malformed envelope with the real data still under `data` (#57).
**Lesson**: the same wrong-nesting-level class as `validate_value_ranges`, and it hid for the same reason — **its failure direction is "there is work to do"**, which reads as a finding rather than as a defect. A gate that over-reports gets investigated; a repair tool that over-reports gets run. Migrate one-shot tools when the envelope changes, or delete them; a tool that only runs during an incident is one nobody exercises between incidents.

### A test that asserts wiring instead of behaviour is green on a no-op (2026-09-02)
`test_all_entsoe_collectors_share_one_host_key` asserted the constructor attribute was set on all six ENTSO-E collectors. It passed while `EntsoeCollector` — the *critical* price feed — never consulted the breaker at all, because it makes one request per fetch and so never calls `_retry_single`. The feature was a no-op on the collector that mattered most and the test could not see it.
**Lesson**: this is the registered-behaviour-silently-no-ops pattern (GoogleWeather, validate_value_ranges, TenneT metadata) reaching a *test*. Assert the observable effect — "open the breaker, call the collector, assert zero requests reached the client" — never that a value was assigned. Same family as the 2026-08-31 "a probe that PRINTS without ASSERTING is green while its claim rots".

### The ENTSO-E API was in scheduled maintenance, not flaking (2026-09-02)
Days 08-29/08-31/09-01 all failed on ENTSO-E 503s and were treated as transient. Probing directly settled it: `web-api.tp.entsoe.eu` returns a byte-identical 18,847-byte branded maintenance page ("Scheduled maintenance is currently underway") to a VALID token, an ABSENT token and a GARBAGE token, with no `Retry-After` and no `X-RateLimit-*`. Not a ban and not a quota — auth is never reached. `web-api`, `tp` and `transparency` all resolve to one Azure IP (20.23.37.29) and the other two answer 200/404, so the edge is healthy and only the `web-api` vhost is switched off.
**Lesson**: to tell "we are blocked" from "it is down", vary the credential and compare bytes — a block discriminates on auth, an outage does not. Two independent networks (Actions runners + local) seeing the same page rules out IP blocking. `transparency.entsoe.eu/api` returning 200 is a red herring: it is the SPA catch-all serving index.html, not an API.

### An instrument whose negative case is silence reads as "no data", not as a failure (2026-08-31) [x2]
Three cache hit/miss greps in one day, each fixing the previous one's blind spot and opening its own, all failing in the SAME direction: a real miss emitted no matching line, which reads as inconclusive rather than as a miss — the direction that cannot refute the change under test. `setup-python` prints `pip cache is not found`; `actions/cache` prints `Cache not found for input keys`; neither substring contains the other. Working form: `grep -aiE 'cache restored from key|cache (is )?not found'`.
Same run found the local instance: all 8 `<!-- verify: -->` annotations passed, exit 0, while two of the claims they annotate were stale (open issues 13 vs 15 measured; repo 797 MiB vs 846 MiB). A probe that PRINTS a value without ASSERTING it is green while its claim rots. Both are recurrences of the promoted "exercise BOTH paths — known-good passes, known-bad fails" pattern (2026-08-08), which did not take because nobody thinks of a grep or an annotation as a guard.
**Recurrence 2026-09-03**: found by /curate in `MEMORY.md` itself. The open-issue annotation `gh issue list --state open --json number | jq length` printed **21** beside a claim of **22** and scored PASS — the count had gone stale within the same session that set it, because closing #52 came after. A probe that prints a value the runner never compares to the claim is decoration. Fixed by making it assert: `[ "$n" -eq 21 ] || exit 1`. The entry recording this lesson was two screens above the defect.

### The same request-not-response defect recurred in a second collector family 16 days later (2026-08-30)
The 2026-08-14 fix was applied to `_openmeteo_shared` only. The four ENTSO-E country-keyed collectors had the identical bug — `_get_metadata` built `country_codes`/`zones` from the configured list — and it stayed invisible until the 2026-08-29 ENTSO-E 503 outage dropped NL while the envelope still claimed it. A fix scoped to the collector family that surfaced the bug is a fix that will recur; when closing one, grep for the shape across every family.
Second lesson from the same change: record delivery against the PARSED data, not the fetch. All four gate `parsed[zone]` on a truthiness check, so a zone can fetch fine and still vanish — an all-NaN series or a frame missing the wanted columns. The first draft recorded at the end of `_fetch_raw_data` and reproduced the very bug it was fixing.

### Reviewing the fix found two blockers the tests and a live reproduction both missed (2026-08-14)
The member-drift fix had a green 751-test suite and a hand-verified end-to-end reproduction against the real sidecar, and still shipped a hole that let `grid_imbalance` drop a published field silently, plus a code path made unreachable by a pre-existing rule. Tests pass on the world the author imagined; the second blocker only existed in production, because the fixture repo had no observation log. Build the fixture with the state production actually has.

### A guard you can delete without a test failing is not a guard (2026-08-14)
`DIAGNOSTIC_ENVELOPE_KEYS` was verified by hand, at the console, and never encoded — replacing it with the identity function left all 757 tests green while silently restoring the publish failure it was written to prevent. Behaviour confirmed interactively is not covered; mutate every new guard and watch a test die before believing it exists.

### A data-quality gate can report "all checks passed" on a half-missing feed (2026-08-23)
`ned_production` returned `forecast` only, no `actual`, for two days — and `[DQ:ned_production] All 4 quality checks passed`. The completeness check counts what is present; it has no notion of a component that must be there but is absent, so "half the feed vanished" reads identical to "data is clean". Same run's drift tripwire caught what the DQ gate should have owned. Fourth instance of the silent quality-gate skip pattern — the fix is a presence check on the expected `actual`/`forecast` components, not another completeness count.

### A merge over shape nodes must not route an unknown `_kind` back into itself (2026-08-23)
`_merge_signatures`/`_conflict_node` recursed unboundedly for two same-kind dict nodes whose `_kind` the merge did not dispatch on — `RecursionError` in the 16:00 UTC run, found by the review battery, not reachable from `compute_shape_signature`'s own output. Fixed with a `_MERGEABLE_KINDS` allowlist plus an `opaque` bucket, pinned by a test. When a merge dispatches on a closed set of kinds, gate on an explicit allowlist and add a test that a novel kind terminates.

### A five-lens review passed two defects that a six-line smoke test caught in seconds (2026-09-04)
The #50 alerting job was reviewed by the full `/review-changes` battery. Only the lens that actually *ran* `gh` found anything; four lenses read the same YAML and found nothing. Two real defects: (1) `gh` resolves its target repo from the git remote, not `GITHUB_REPOSITORY`, and the job has no checkout — so every call died with `fatal: not a git repository`, which `continue-on-error` rendered as a green job that alerted nobody; (2) dedup via `gh issue list --search "... in:title"` missed an issue created ~4s earlier, because GitHub's search index is eventually consistent, so back-to-back failures each opened a duplicate. `--label` as a server-side filter lagged the same way. Only the unfiltered list is read-after-write consistent. The first fix I reached for was itself wrong, and only running it showed that too.
**Lesson**: for anything that talks to an external API, a smoke test outranks any number of reading passes — reviewers test against already-settled state (an indexed issue, a resolvable remote) and cannot see a consistency model. Write the create-then-immediately-read step explicitly; that single step found both. `scripts/smoketest_alerting.sh` is the durable form.

### A shape signature cannot see span, so a critical feed halved its horizon unnoticed (2026-09-04)
`load_forecast` (a CRITICAL_FEED and an Augur model input) shipped 96 points / 1 day instead of 192 / 2 days for four consecutive publishes from 08-28, and nothing in the pipeline objected — 96 records and 192 records hash *identically*, because the signature captures structure, not extent. `metadata.end_time` kept declaring +2 days, so the envelope over-declared its own coverage. The only thing that noticed was the downstream consumer's t0 hold-back. Adding feeds to `CRITICAL_FEEDS` does not help this class at all. Root cause was upstream ENTSO-E A65 (both zones lost day-ahead 08-28; NL recovered by 09-04, DE_LU still short) — not our parser, which builds each zone's timestamps from that zone's own series with no cross-zone alignment.
**Lesson**: a gate covers exactly one of {presence, structure, span, values} — name which, and never let a registry of "important" inputs imply the rest. `CRITICAL_FEEDS` is a presence-and-structure registry whose name reads like an importance registry, which is how it got mistaken for span cover. A span check is a separate missing instrument; it needs a per-source expected span (NL and DE_LU publish day-ahead on different schedules) and a minimum-observations floor before trusting a derived expectation.

### A derived classification with no evidence threshold learns from noise (2026-09-04)
`derive_volatile_feeds` classifies a feed as shape-volatile on `>1 distinct hash` in the window. `wind_forecast` was permanently declassified — losing drift enforcement — off **two one-off excursions in 60 runs**, against a dominant shape present in the other 58. Same for `nordic_hydro`, which self-healed out of blocking after a single bad day. That self-healing was initially read as the mechanism working as designed.
**Lesson**: `>1 observation` is not evidence of churn. Any derived expectation (volatility, span, range) needs a minimum-observations floor and a share test — "this shape appeared in 2 of 60 runs" is an excursion, not variability. Do not read a feed's auto-declassification as proof it churns.

### Classify every monitor as presence-of-failure or absence-of-success (2026-09-04)
The #50 alerting job is triggered BY a workflow run, so it detects a run that FAILED and is structurally blind to a run that never FIRED — a dropped cron, a disabled workflow, a queue outage. For the 08-31..09-03 outage it would have fired on all five days; had the cron simply stopped, it would have been silent on all five. #50's title is "Scheduled publish silently skips whole days", so the fix covers part of its own issue and not all of it. Augur's downstream t0 hold-back notices the ABSENCE of a fresh vintage and is the only detector that covers the silent case.
**Lesson**: presence-of-failure and absence-of-success are different detectors and neither substitutes for the other — classify every monitor as one or the other and say which. Operational corollary agreed with the consumer: *their alarm firing with no issue on our side is worse news than an issue existing*, because it means the pipeline is not running at all rather than running and failing. This is the {presence, structure, span, values} idea moved from data gates to monitors. Third instance in one day of the same shape — a check that works on every day it is exercised and is absent on the day the failure takes another form (the other two: a credential adequate for reads and not writes; a shape signature that cannot see span).

### Two liveness gaps across the estate, both self-hosted, no off-host watcher (2026-09-04)
A liveness check cannot live inside the thing it watches. energydatahub's alerting runs as a job of the workflow it monitors, so it cannot report that workflow not running. Augur's `heartbeat_check.sh` runs on sadalsuud, so it cannot report sadalsuud being down — declined as a new-service cost in July, and that decision stands. So both halves of the pipeline have the same accepted blind spot and nothing watches from outside.
**Lesson**: recorded as an accepted risk, NOT a proposal — closing it means a new always-on external service, which is a cost decision for the maintainers, not something to build on agent initiative. If it is ever taken up, the requirement is one off-host watcher that fires when a publish has not landed for N hours; it does not need to be clever, only elsewhere.

### Naming a confound and then predicting through it (2026-09-04)
Registered a falsifiable prediction with the downstream consumer — NL 192/2, DE_LU 96/1, price 192/2 — having explicitly written one message earlier that "a 09:59 probe cannot distinguish a DE_LU gap from German TSOs publishing later than Dutch". Predicted DE_LU anyway. It was falsified within the hour by our OWN 08:14 UTC publish, which carried DE_LU at 192/2: it had recovered inside the 15 minutes since the probe. The evidence was on disk in this repo before the consumer pointed at it, and it went unread because the probe had already been treated as decisive.
**Lesson**: naming a confound and then predicting through it is worse than not noticing it — it converts a known unknown into a stated claim. Withhold the leg the confound touches; a partial prediction is worth more than a contaminated one. Generalises to any pre-committed criterion: the test is not "can this measurement be taken" but "can it tell the alternatives apart", so a criterion that needs a caveat attached is a criterion that is wrong. A probe at one instant cannot separate "absent" from "not published yet" for a source whose publication schedule is unknown — that needs two probes or a known schedule.

### Three wrong records in one session, all from trusting a summary over a reachable artifact (2026-09-04)
Four wrong records across two repos in one day, and none was caught by care. (1) "load_forecast is same-day by construction" — generalised from ONE decrypted vintage against a two-week baseline in the same directory; killed by decrypting the archive. (2) A time box on the drift gate, designed and approved, whose only reachable domain turned out to be the feeds that must never be waved through; killed by the review battery. (3) The alerting described as the consumer's best outage signal when it cannot see a run that never starts; killed by re-reading the workflow. (4) The consumer's own "design around the 18h shortfall", which came from *our* single-vintage claim and was held until the archive read.
**Lesson**: in every case the artifact that settled it was already reachable and the summary was believed instead — including summaries written an hour earlier by the same session. When a peer or a past self hands you a conclusion, the cost of re-deriving it from the artifact is almost always lower than the cost of it being wrong. Cross-session status arrives with the confidence of a commit and the durability of a plan; stamp announced-but-unreviewed work "proposed, not shipped" and sequence nothing behind it until there is a commit to point at.

### Tightening the drift classifier would cost more availability than it buys (2026-09-04)
Measured every published feed over a 60-run window: distinct shapes and the dominant shape's share. It splits cleanly at ~90%. The three genuinely churning feeds — `calendar_features` 67% (5 shapes), `air_quality_buurt` 86%, `cross_border_flows` 87% — are exactly the three hand-declared `VOLATILE_SHAPE_FEEDS`, so the original curated list was right. The five feeds that are only *derived* volatile are stable ones with 1-4 bad days out of 60: `ned_production` 93%, `wind_forecast` 97%, `market_proxies` 97%, `generation_mix` 98%, `nordic_hydro` 98%.
**Lesson**: the `>1 distinct hash` rule is imprecise, and that imprecision is LOAD-BEARING for availability — those five feeds' excursions are currently absorbed as warnings. Adding a 90% share floor would classify them correctly and return all five to enforced, costing roughly **a blocked publish every six days**. Do not tighten the classifier while the gate's only response to drift is withholding all 20 feeds. The precision fix is only affordable once detection is decoupled from blocking (warn + alert instead of fail). Same conclusion the abandoned time box reached from the other side: the lever is wrong, not the membership.

### CRITICAL_FEEDS' only lever is withholding the whole publish (2026-09-04)
`wind_forecast` backs a live Augur feature (`wind_speed_80m`) and had auto-classified as derived-volatile, so its drift could no longer block. A branch adding it to `CRITICAL_FEEDS` was written, reviewed, and then **closed unmerged** on the measurement above: promotion moves it to enforced at ~1 blocked publish/month, and blocking does not FIX a degraded feed — it withholds 19 healthy ones. The consumer already detects wind degradation after ingestion via its own t0 hold-back, so the failure was already detected, just later.
**Lesson**: before adding a feed to a blocking registry, ask what blocking BUYS for that feed. If the degradation is already detected downstream and the remedy is "publish nothing", the registry is the wrong instrument. `CRITICAL_FEEDS` is right for a feed vanishing entirely or an unversioned schema break; it is wrong for data-driven excursions on a feed the consumer can already see degrade.

### A grace that tests a different predicate than the gate it forestalls is dead on arrival (2026-09-10)
Registered `ned_production` in `PRESENT_EMPTY_GRACE_FEEDS` so a total NED.nl outage would stop aborting the publish (run `34392331572`, 19 healthy feeds lost). The guard tested `not ds.data`; `collectors/ned.py:255` seeds `parsed[energy_type] = {}` for every configured type *before* it knows whether anything parsed, so the outage envelope is `{'solar': {}, ...}` — truthy, zero points. The registration, the coercion branch and 14 green tests were all inert, and the incident would have replayed unchanged.
**Lesson**: a guard must ask the SAME question as the gate it exists to pre-empt — here `_count_data_points(...) == 0`, which is literally the expression `validate_completeness` uses — not a proxy that happens to agree for the feeds you tested it on. Truthiness agreed for the six Open-Meteo feeds, which gate their per-location assignment on `if location_data:`; it disagreed for the seventh, and the disagreement was invisible because no test built an envelope. Predicate now lives in `present_empty_feeds()` so both sides read one expression.

### Asserting the wiring instead of the behaviour passes on dead code (2026-09-10)
The tests written alongside the above grepped `inspect.getsource(data_fetcher.main)` for `'ned_production':` and `if 'ned_production' in _coerce:`. Both false-passed: the first string also occurs in the unrelated `quality_datasets` map, so deleting the candidate entry left the test green; the second ignores the assignment target, so `... : buurt_solar_data = None` would pass. 17 tests green over a guard that could not fire.
**Lesson**: a test that reads source text asserts that someone typed something, not that anything happens. Build the real object the collector produces and assert the predicate classifies it. Where a structural check genuinely is the right tool — registry vs orchestrator wiring — parse the AST for the dict literal rather than grepping, and ablate it (delete the entry, watch it go red) before believing it.

### A recovery publish before the day-ahead auction is worse than no publish (2026-09-10)
Dispatched `34450530525` at 07:33 UTC to close a ~48h gap for Augur. It succeeded, deployed, and closed the alert — and shipped `entsoe` at **96 points, same-day only**, because tomorrow's day-ahead auction had not cleared. Downstream that is not a smaller win, it is a loss: their gate consumes the half-size vintage, marks it, and then skips the healthy ~18:00 publish as not-strictly-newer. Measured bound from our own runs: 2026-09-04's 10:17 UTC dispatch got 96, its 18:47 UTC scheduled run got 192.
**Lesson**: "restore the feed sooner" is not automatically better when the feed has a publication schedule upstream of ours. Before dispatching a recovery run, ask what the *upstream* has published yet — not just whether our pipeline is healthy. Dispatch early to test the pipeline; wait for the scheduled run to restore the data. Now in CLAUDE.md's "How to Work Here" next to the dispatch command.

### Upstream can answer a 4-day query with 1 day and nothing anywhere says so (2026-09-10)
Root-caused #74's unexplained scheduled shorts by diffing collect logs. Same query, same window, same pagination: `09-06 Parsed 192 data points from ENTSO-E response` vs `09-08 Parsed 96`. No HTTP error, no retry, no 429 on the price path. ENTSO-E answered a four-day NL day-ahead query with one day — and the missing days included 09-07, already in the past. **Fourth instance of request-vs-response** after locations (08-14), zones (08-30) and borders (#54); the first where nothing caught it, for 9 days.
**Lesson**: the first three were caught by the drift tripwire aborting the publish — i.e. by an instrument that was not designed for them and responded by breaking everything. Span is the axis where that accident does not happen, because 96 and 192 hash identically by construction. When adding a collector, record what was REQUESTED next to what was DELIVERED; a count in the envelope that nobody compared to the ask is not a measurement.

### Publishing on a schedule hides how often the payload is short (2026-09-10)
Decrypting the last 14 `energy_price_forecast.json` vintages: **8 are half-size** (96 points, same-day only) and 6 are the healthy today+tomorrow 192. Nobody noticed, because every gate was green throughout — the shape signature hashes 96 and 192 identically by construction, and the span check built for exactly this (#53) reports `members_with_expectation: 0` since no member yet has its 10-observation floor. The consumer noticed, via a median that had decayed from 192 to 96 underneath their gate.
**Lesson**: a gate that is deployed but not yet armed reads identically to a gate that is passing, and this repo now has that failure twice (the span reporter's "nothing verified" vs "all clean", 2026-09-04). When shipping a detector with a warm-up period, state the warm-up in the thing that consumes it, and treat the window before it arms as uncovered rather than as clean.

### A gate exemption does not reach the evidence the classifier learns from (2026-09-21)
The drift tripwire learned to excuse `collector_quality_issues` churn, but `_shape_observations.jsonl` still recorded the RAW hash, so the excused flip still counted as "this feed wobbles" — one flip would have made `grid_imbalance` derived-volatile and downgraded every real break on it for 60 runs. Fixed by recording a diagnostic-blind hash beside the raw one.
**Lesson**: when you teach a gate to ignore something, ask what else consumes the same signal. Detection, downgrade and *learning* are three consumers here, and only the first two live in the tripwire.

### A copied path list is not the predicate it stood for (2026-09-21)
Corrected a project review lens whose trigger read `scripts/**` when the rule was "contains shell or YAML" — then wrote the identical error one section above it, claiming "any change under `scripts/**` forces full depth" when the framework's carve-out is "any shell script or executable". A mode-644 Python file matches the path and not the predicate.
**Lesson**: a path glob is evidence for a predicate, never the predicate. When copying a rule, copy the condition and re-derive the paths — and note this was caught by the review of the very commit that introduced it, not by re-reading.

### Ablating the wrong function reads exactly like a passing ablation (2026-09-21)
Patched `if kind in ("timestamp_map", "list")` to disable a prune branch; the same line exists in `_merge_signatures` earlier in the file, so the edit hit that instead. Target tests stayed green — which I nearly recorded as "the branch is dead code" — and three unrelated merge tests went red, which is the only reason it surfaced.
**Lesson**: an ablation must fail the tests it targets. If the ablation is green, suspect the ablation before concluding anything about the code, and run the FULL suite so a mis-aimed patch has somewhere to show up.

### Re-fetching the window turns an opaque hash flip into a measured cause (2026-09-21)
`load_forecast` failed the tripwire with only two hashes to show for it. Re-fetching the same window from ENTSO-E a day later, then stripping candidate fields from the live payload and re-hashing, reproduced the exact failing hash and named both causes in ~10 minutes.
**Lesson**: the sidecar stores hashes, not reasons, but the upstream API still has the window. Reconstruct rather than infer — and a hash that matches byte-exactly is proof, where a plausible story is not. (#48 asks for the tripwire to report this itself.)

### A fake clock that sums sleeps makes concurrent retry tests pass anything (2026-10-05)
The first storm-replay test advanced one shared fake clock by every `asyncio.sleep`. Twenty-five concurrent locations therefore added their sleeps end to end and "outlasted" a 61 s storm under the OLD 3 s retry budget too. It passed on the pre-fix code, and only the deliberate run against `git show HEAD:` caught it. Rewritten on the real clock with every delay scaled down 100×.
**Lesson**: a fake clock is sound for ONE task. For concurrent tasks, scale real time instead, and always run a regression test against the unfixed code before trusting it.

### A late cron rolls the collection window past local midnight (2026-10-06)
GitHub started the 16:00 UTC cron at 22:16 UTC on 10-05 = 00:16 Amsterdam, so `today` became 10-06, tomorrow's day-ahead did not exist, `generation_forecast` came back empty and the drift gate lost the publish (run `37381385635`; also the cause of the 14-member span shortfall that run). Scheduled runs now export `COLLECTION_DATE` = the cron's UTC date and `resolve_collection_day()` anchors on it; holds while the delay stays <8h. If a late run fails again, check `grep 'Late scheduled run'` in its log first.
