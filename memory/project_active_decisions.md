# Active decisions

Moved verbatim from `memory/MEMORY.md` on 2026-10-05. Read before changing severities, adding a collector against a shared host, adding a registry entry, or building/loosening a guard.


- Market history stored as separate `market_history.json` (not in `market_proxies.json`) to avoid breaking existing consumers
- Generation mix uses same `EntsoeGenerationCollector` class with expanded params, separate from French nuclear `generation_forecast.json`
- Time resolution: store each source at native resolution, defer alignment to consumers — see [ADR-001](../docs/decisions/ADR-001-time-resolution-strategy.md)
- In-repo memory (this file + topic files) over auto-memory, per agent-ready-projects ADR-001
- **`DATASET_MISSING_SEVERITY['entsoe'] = 'critical'` is load-bearing for Augur's training target — do not relax it without telling them first.** Measured downstream 2026-09-01: their consolidate.py (Augur repo) merges `("elspot", "epex", "entsoe")` with later-writes-win, so when entsoe is absent the *worst* source becomes the target. Against entsoe, `epex` runs mean +16.13 EUR/MWh (MAE 21.16, corr 0.859) while `elspot` runs +0.86 (MAE 9.02, corr 0.954); the offset is flat across lags -4h..+4h, so it is a level bias, not a misalignment. **The epex path is already live, not hypothetical**: 93 of 8013 parquet hours (1.16%) are epex-sourced, ongoing through 2026-08-27, and on the 43 where elspot was also available epex overwrote it by mean +30.12. The fail-closed gate is what bounds that at 1.16% instead of absorbing a whole multi-day outage — 08-31 alone would have been a full day at a +58 offset, inside their 56-day rolling window. Publishing a partial price feed would also not have saved the vintage: `load_forecast` is entsoe-only and in their `FEATURE_COLUMNS`, so their `t0` anchor stalls regardless.
- **Publish what was DELIVERED, never what was configured.** `_get_metadata` restating the request cannot detect anything. Fixed for locations in `collectors/_openmeteo_shared.py` (2026-08-14, `record_location_delivery`) and for ENTSO-E bidding zones in `collectors/_entsoe_shared.py` (2026-08-30, `record_zone_delivery`) — the same bug, found twice, 16 days apart. Measure at `_validate_data` against the parsed data, not at `_fetch_raw_data`: a zone/location can fetch and still be dropped by the parser. The time axis (delivered span vs requested window) has no equivalent check yet.
- OpenMeteo `OPENMETEO_SEMAPHORE_CAP` = collector count (not lower) — empirically required to avoid Open-Meteo's CDN per-source cooldown affecting late-scheduled collectors. See `collectors/_openmeteo_shared.py` docstring.
- **Multi-collector concurrent upstream pattern**: when adding a new collector that hits an API already used by other collectors, assume the upstream applies per-source rate-limits, CDN cooldowns, or "no data" 4xx responses that look like transients. Six incidents in `memory/gotcha-log.md` (ENTSO-E 503 cascade, Luchtmeetnet 429, Open-Meteo 429 storm, Open-Meteo CDN cooldown timeout, TenneT 422→429, the 2026-08-29 ENTSO-E 503 outage) all share the same shape. Default prescription: (1) shared semaphore cap ≥ collector count, (2) per-location retry with exponential backoff, (3) classify non-retryable HTTP statuses (422/400/401/403/404) at the collector level instead of letting BaseCollector retry them. See `collectors/_openmeteo_shared.py` for the cap pattern and `collectors/_http_classifier.py::raise_if_permanent` for the canonical HTTP-status bail-out (extracted from `tennet.py` on 2026-06-07 specifically so the next ENTSO-E/NED/GIE incident is two lines away from being fixed). Any `_fetch_raw_data` permanent-exit path MUST raise `NonRetryableError`, never plain `Exception`/`ValueError` — the outer retry loop catches anything else. Fourth prescription added 2026-09-02 (#52): if the host is already hit by another collector, pass `host_breaker_key` — per-instance breakers cannot see a host-wide outage, and classify "answered fine, no rows" errors as non-host or a healthy source will trip it.
- **Parallel hard-coded registries**: when you see two-or-more parallel lists keyed on the same identifier (anywhere — Python, YAML, JSON, doesn't matter), consolidate before adding the third instance. Two incidents: `data_quality.py` had 3 lists for missing-dataset severity (collapsed in 39a94d6 to one `DATASET_MISSING_SEVERITY` dict); `collect-data.yml` had 2 lists for publishable feeds (completeness tripwire at line 54 + docs-prepare at line 118) — adding #3's `nordic_hydro` to one but not the other was the BLOCKER flagged by the multi-model review battery on c40a53b. Hard rule: when adding the third item, collapse OR add a test that asserts the lists match.
- **Warn-only bedding-in audits**: when flipping any CI guard from `--warn-only` to fail-mode, audit the actual warnings emitted during the bedding-in window — don't just count green runs. Two incidents: the 2026-06-08 catalog-drift warning was on the record but unread (run was overall green); the `_TS_PATTERN` date-only false-positive class was swallowed for the entire bedding-in period and only surfaced when fail-mode flipped on 2026-06-10. Corollary: introspection tools (shape_signature, drift detectors) have their own assumptions — exercise them against real published payloads, not just synthetic fixtures, before trusting them as gates.
- **A check must report its DENOMINATOR, not just its verdict** (promoted 2026-09-04, after the silent-skip pattern recurred for the 5th time): "0 problems found" and "0 problems findable" are the same string and different facts. The span check (#53) shipped reporting "every member carries its usual number of days" on a run where ZERO members had enough history to be judged — written by the session that had just logged three entries about this pattern, about an hour apart, inside the check built to close a gap of this kind. It was caught by reading a production run log; 43 tests passed because every one asserted the verdict and none asserted the denominator. Prescription: emit `M of N judged` from the code, gate any downstream consumer on a `checked` flag that is false when nothing was judged, and assert the denominator in tests. See `utils/span_signature.py::evaluate_spans` and `scripts/report_span_shortfall.py` for the shape.
- **Silent quality-gate skip** (3-incident pattern, broadened 2026-06-08): a registered behaviour that's expected to enforce/surface something silently no-ops at a downstream layer, and the absence looks identical to "data is clean". Three incidents now: GoogleWeather `API_KEY_INVALID` returned success exit codes for 7 months while the API was 401-ing every call (validator path); `validate_value_ranges` silently no-op'd on 2-level-nested feeds for ~3 months (validator path); TenneT custom `collect()` override bypassed BaseCollector's metadata auto-inject so `balance_delta_status` + `collector_quality_issues` populated correctly in memory but never reached the published file (publish-path drop, 2026-06-08 dispatched-run discovery — `ab3dcd4`). Hard rule, now generalised: when wiring a new field/check/signal, **trace it end-to-end through every layer until you observe it on disk or in the operator log**. Don't trust that "registered = surfaced". Two-layer corollary: when overriding a BaseCollector method, audit the WHOLE contract (reset → fetch → parse → normalize → validate → metadata → inject → dataset), not just the parts the override touches. Pattern signature: unit tests green, live run silently drops the new field.
- **Derive classifications from history, don't hand-maintain exception lists** (2026-06-14): a hand-curated allowlist of known-bad cases is *reactive* — it only protects against what already broke, never the next instance. The schema-drift `VOLATILE_SHAPE_FEEDS` allowlist grew 1→3 in two days (air_quality_buurt 06-13; cross_border_flows + calendar_features 06-14), each added only *after* it failed a production run. Fix: `scripts/detect_schema_drift.py::derive_volatile_feeds()` derives the volatile set from committed shape history (>1 hash at the same schema_version = data-driven churn), unioned with the declared seed. This got *ahead* of the problem — on first run it proactively flagged `grid_imbalance`/`market_history`/`market_proxies`, three not-yet-broken feeds. General rule: when you catch yourself adding the Nth entry to a hand-maintained exception list for the same recurring class, ask whether the membership can be *computed* from observed history/state instead. Irreducible residual: the very first occurrence of a novel case still can't be auto-distinguished from a real problem (nothing to compare) — but that's once-per-case, not the recurring pain. Sibling to "warn-only bedding-in audits" (both about not trusting a guard's surface-green state). **Known limit, found 2026-08-08:** a history-derived classifier only learns from observations that get *recorded*. The drift tripwire (`collect-data.yml:119`) runs before the commit step (`:149`), so a run it fails commits no sidecar — and `derive_volatile_feeds()` therefore never sees the drift that tripped it. Run `30838120578` failed on `ned_production`/`wind_forecast` on 08-03 and neither is classified five days later. When you build a self-classifying guard, check that the failing path still writes the evidence, or it can only ever learn from its own near-misses. Tracked as H3 in `memory/hypothesis-log.md`.
- **Guard signal integrity — always-red is as corrosive as always-green** (2026-08-08): the existing decisions above cover guards that silently pass. The inverse costs the same. The new verification hook's workflow-YAML branch failed 100% of the time on a valid file, with a message asserting the daily run would fail to start (PyYAML missing; `run()` could not distinguish `ModuleNotFoundError` from a parse error). A guard that always fires trains you to disable it exactly as fast as one that never fires trains you to trust it — and the disable is permanent while the outage is not. Hard rule: when adding a guard, exercise BOTH paths before shipping — see it pass on known-good input and fail on known-bad. The hook's own docstring says it ("a hook you have not seen fail is a hook you cannot trust"); it shipped without either path having been run against a real workflow file.
